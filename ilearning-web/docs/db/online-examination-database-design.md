# Online Examination System 数据库设计说明

本文档以当前 11 张表的最终 SQL 为基准，重点解释各表的业务职责、领域边界、关键字段的设计意图，以及表之间的协作关系。对于 `id`、`created_at` 等含义明确的通用字段，不逐一展开。

## 1. 整体领域模型

系统的核心业务链路是：

```text
题库管理
question_bank → question → question_option
    ↓
试卷管理
paper → paper_question
    ↓
考试活动
exam
    ↓
考生作答与成绩
exam_attempt → exam_answer

用户与权限：user、role、user_role
```

系统包含三个需要严格区分的概念：

- **题目（Question）**：可被复用和维护的题库内容。
- **试卷（Paper）**：一组确定的题目、顺序和分值。
- **考试（Exam）**：一次面向考生开放的考试活动，引用试卷并定义参与规则。

考生参加的不是抽象的题库，也不是直接编辑中的试卷，而是某个考试活动；每次参加都会产生独立的考试记录。

## 2. 11 张表的职责与边界

| 表 | 核心职责 | 不负责的事情 |
|---|---|---|
| `user` | 用户账号、认证凭据、账号状态 | 用户角色的分配关系 |
| `role` | 定义系统角色及其业务编码 | 用户与角色的关联 |
| `user_role` | 建立用户与角色的多对多关系 | 角色权限细粒度配置 |
| `question_bank` | 管理题库的名称、排序和可用状态 | 题目内容本身 |
| `question` | 管理题干、题型、难度、解析等 | 试卷中的题序与分值 |
| `question_option` | 管理选择题选项及正确选项标记 | 考生实际选择了什么 |
| `paper` | 管理试卷本身及其总分、状态 | 考试时间、考试次数 |
| `paper_question` | 维护试卷题目清单、题序、分值及题目快照 | 考生的作答和成绩 |
| `exam` | 管理考试活动的开放时间、时长、次数和及格线 | 某个考生的具体考试过程 |
| `exam_attempt` | 管理考生每次考试的生命周期与总成绩 | 每道题的具体作答内容 |
| `exam_answer` | 记录每道试卷题目的作答、判题与得分 | 考试活动的开放规则 |

这里最重要的职责划分是：**`paper` 描述考什么，`exam` 描述怎么考，`exam_attempt` 描述某次实际参加考试的过程。**

## 3. 核心业务设计

### 3.1 题库与题目：内容管理和考试使用分离

涉及 `question_bank`、`question`、`question_option`。

#### `question_bank` — 题库

负责对题目进行分类组织，例如“羽毛球规则题库”“安全培训题库”。

- `sort`：题库在管理界面或列表中的展示顺序，不影响题目在试卷中的顺序。
- `status`：题库是否启用。禁用题库后，应用层应限制继续从该题库新增或选取题目，但历史考试记录仍须可查询。

#### `question` — 题目

保存题目本身的内容与分类属性。

| 字段 | 设计意图 |
|---|---|
| `question_bank_id` | 指定题目所属的题库。一道题在当前模型中只归属于一个题库。 |
| `question_type` | 决定作答组件、答案结构和判分策略。`1` 单选、`2` 多选、`3` 判断、`4` 简答。 |
| `difficulty` | 题目难度等级，可用于筛选和组卷；目前只有三个固定等级。 |
| `content` | 题干正文，使用 `TEXT` 支持较长文本。 |
| `image_url` | 题干关联图片的地址，与正文分离，避免把图片内容直接塞入题干文本。 |
| `analysis` | 题目解析，供交卷后的结果页或复习页面使用。 |

`question.status` 表示题目当前是否可用。禁用题目不应自动删除已经发布的试卷内容或历史考试数据。

**边界：** 题目是可维护的源数据，不应直接承担试卷中的题序、分值等上下文信息。同一道题进入不同试卷时，可以具有不同的顺序和分值。

#### `question_option` — 选项

存储选择题、判断题的选项及标准答案标记。

| 字段 | 设计意图 |
|---|---|
| `question_id` | 标识选项所属题目。 |
| `option_key` | 选项的稳定标识，例如 `A`、`B`、`C`，可用于答案表达、导入导出和题目快照。 |
| `is_correct` | 标记该选项是否属于标准答案。多选题允许多个选项为正确答案。 |

当前唯一约束 `uk_key (question_id, option_key)` 保证同一道题不能存在重复的选项标识。

题目类型与选项数据之间的规则由应用层维护，例如：

- 单选题：应有且只有一个正确选项。
- 多选题：至少有两个正确选项。
- 判断题：需要统一采用两个选项，或采用独立的布尔答案模型；当前表结构更适合前者。
- 简答题：通常不需要选项，答案及评分规则应由应用层处理。

这些属于业务校验，不能仅凭当前 DDL 自动保证。

### 3.2 试卷与试卷题目：定义一份确定的考试内容

涉及 `paper`、`paper_question`。

#### `paper` — 试卷

负责管理试卷的基本信息、总分和生命周期。

| 字段 | 设计意图 |
|---|---|
| `total_score` | 试卷的理论满分，应该与所有试卷题目分值之和一致。 |
| `status` | `0` 草稿、`1` 已发布、`2` 已归档，控制试卷的使用状态。 |
| `created_by` | 创建人，用于归属、审计和管理端权限校验。 |

试卷本身不配置考试开放时间和参加次数。这些属于考试活动的职责。

#### `paper_question` — 试卷题目

这是连接题库内容与试卷内容的关键表。一条记录表示某道题在某份试卷中的一次使用。

| 字段 | 设计意图 |
|---|---|
| `paper_id` | 所属试卷。 |
| `question_id` | 指向题库中的源题目，用于追溯题目来源。 |
| `sort` | 该题在试卷中的展示顺序。 |
| `score` | 该题在当前试卷中的满分；同一道源题在不同试卷中可以有不同分值。 |
| `question_snapshot` | 保存发布时的题目内容快照，使考试内容不完全依赖源题目当前状态。 |

这里有两项重要约束：

- `uk_sort (paper_id, sort)`：同一份试卷不能有重复的题目顺序。
- `uk_question (paper_id, question_id)`：同一道源题不能在同一份试卷中重复出现。

**为什么需要 `question_snapshot`？**

假设一份试卷已发布，题干是“羽毛球单打场地宽度是多少？”，正确答案为 A。后来管理员修改了题库中的题干或选项。如果考试仍然实时读取源题目，历史考试可能会出现题目与答案不匹配的情况。

快照用于固定试卷发布时的内容，通常应包含：

- 题型、题干及题干图片地址；
- 选项标识、选项内容、图片地址和展示顺序；
- 标准答案；
- 解析。

其中标准答案和解析属于服务端敏感数据，考试作答接口不能直接把完整快照返回给考生。

快照的具体 JSON 结构应由应用层统一定义并进行版本管理，不能依赖前端随意拼装。

### 3.3 考试活动：配置考试规则

涉及 `exam`。

一份试卷可以被不同考试活动复用。例如，同一份培训试卷可以分别用于月度考试和补考活动，两者的开放时间、考试时长和及格线可以不同。

| 字段 | 设计意图 |
|---|---|
| `paper_id` | 指定本次考试使用哪份试卷。 |
| `duration_minutes` | 单次考试的时长，`0` 表示不限时。 |
| `max_attempts` | 每位用户允许参加的次数，`0` 表示不限次数。 |
| `passing_score` | 本次考试活动的及格分数，不必与试卷总分相同。 |
| `start_time`、`end_time` | 控制考试活动的开放时间范围。允许为空意味着必须在业务层明确空值的语义，例如不限开始时间或不限结束时间。 |
| `status` | `0` 草稿、`1` 已发布、`2` 已关闭。用于控制活动生命周期。 |
| `created_by` | 创建人，用于管理权限与审计。 |

需要区分**活动状态**与**开放时间**。即使 `status = 1`，如果尚未到开始时间，也不能参加；即使仍处于开放时间内，`status = 2` 也应阻止新考试开始。

发布前至少应校验：

1. 关联试卷已发布且符合使用条件。
2. 试卷总分与题目分值之和一致。
3. `passing_score` 不大于试卷总分。
4. `start_time`、`end_time` 的先后关系合法。
5. 时长和考试次数符合预期。

### 3.4 考试记录与答案：一次考试一份独立记录

涉及 `exam_attempt`、`exam_answer`。

#### `exam_attempt` — 考试记录

一条记录代表某个用户参加某个考试活动的一次考试过程，而不是整个考试活动的定义。

| 字段 | 设计意图 |
|---|---|
| `attempt_no` | 用户在该考试活动中的第几次考试，从 1 开始。 |
| `status` | `1` 进行中、`2` 已交卷、`3` 已判分、`4` 已取消。用于驱动考试生命周期。 |
| `total_score` | 本次考试开始时确定的试卷满分快照。 |
| `passing_score` | 本次考试开始时确定的及格线快照，避免后续活动规则修改直接改变历史判定基准。 |
| `user_score` | 本次考试最终获得的总分；判分完成前允许为空。 |
| `is_passed` | 是否通过考试。判分完成后再确定，未判分时允许为空。 |
| `started_at` | 实际开始作答的时间。 |
| `deadline` | 本次考试的截止时间。限时考试通常按开始时间加时长计算；不限时考试可以为空。 |
| `submitted_at` | 实际交卷时间。 |
| `graded_at` | 判分完成时间。 |
| `time_spent_seconds` | 本次考试耗时，便于统计和结果展示。 |

`uk_user_exam_no (user_id, exam_id, attempt_no)` 确保同一用户在同一活动中不能出现重复的考试序号。

但该约束**不能单独保证考试次数不超限，也不能阻止同一用户同时创建多个进行中的考试记录**。这些必须在服务端通过事务、锁或其他并发控制手段实现。

#### `exam_answer` — 考试答案

每条记录对应某次考试中的一道试卷题目。

| 字段 | 设计意图 |
|---|---|
| `exam_attempt_id` | 所属考试记录。 |
| `paper_question_id` | 指向该题在试卷中的具体记录，而不只是源题库题目。 |
| `answer_content` | 统一承载不同题型的作答内容，例如选项标识数组、判断值或简答文本。 |
| `is_correct` | 客观题的判题结果；尚未判题或需要人工判分时可以为空。 |
| `score` | 当前题目的满分。 |
| `actual_score` | 本次实际得分，允许为空，表示尚未完成评分。 |
| `answered_at` | 最近一次有效作答的时间；未作答时为空。 |

`uk_attempt_question (exam_attempt_id, paper_question_id)` 保证同一次考试中每道试卷题目最多只有一条答案记录。因此，考生修改答案时通常更新已有记录，而不是不断插入新记录。

这里的 `score` 和 `actual_score` 含义不同：前者是可得分上限，后者是实际获得的分数。若后续调整字段名，`max_score` 会比 `score` 更直观，但不影响当前模型的业务含义。

**判分边界：**

- 单选题、判断题：通常按标准答案自动判分。
- 多选题：需要明确采用完全匹配、部分得分还是其他规则。
- 简答题：可能需要人工判分或单独的评分规则。
- 总分：应以每道题的实际得分汇总计算，并在事务内完成必要的状态更新。

`is_correct` 不能完全表达复杂评分结果。例如，多选题可能部分得分但不完全正确，因此实际分数应以 `actual_score` 为准。

## 4. 用户与角色

### `user`

保存登录账号、密码凭据和账号状态。

`password` 应保存经过适当密码哈希算法处理的结果，而不是明文密码；字段名虽然叫 `password`，其业务含义应在应用层明确为密码哈希值。

### `role`

定义角色字典，例如 `ADMIN`、`EXAMINEE`。`role_code` 是供代码和权限判断使用的稳定编码，`role_name` 是供管理界面展示的名称。

### `user_role`

连接用户与角色，允许一个用户拥有多个角色，一个角色分配给多个用户。复合主键 `(user_id, role_id)` 本身就能防止同一关联被重复插入。

当前模型只包含**角色分配**，尚未设计菜单权限、操作权限或资源级授权。如果后续需要细粒度权限控制，应再独立建模，而不是将权限字段直接塞进 `role`。

## 5. 关键业务流程与数据一致性

### 5.1 从建题到发布考试

```text
阶段一：维护题库
创建题库、题目和选项，校验题型、标准答案及选项顺序
    ↓
阶段二：组卷与发布
创建试卷、选择题目、设置题序和分值；校验总分并生成题目快照
    ↓
阶段三：创建考试活动
引用已发布试卷，设置时长、参加次数、开放时间和及格线
    ↓
阶段四：考试、交卷与判分
创建考试记录，保存逐题答案，计算得分并更新考试状态
```

### 5.2 必须由应用层保证的约束

当前 DDL 不使用外键，因此下列约束必须由服务端负责。

| 约束 | 校验时机 |
|---|---|
| `question.question_bank_id` 对应有效题库 | 创建或修改题目 |
| 选项属于指定题目 | 保存选项、批量调整选项顺序 |
| 试卷题目属于有效源题目 | 组卷、发布试卷 |
| 试卷满分等于题目分值总和 | 发布试卷 |
| 考试引用的试卷满足发布条件 | 发布考试活动、开始考试 |
| `paper_question_id` 属于当前考试使用的试卷 | 创建或修改答案 |
| 用户未被禁用且有权参加考试 | 开始考试、提交答案 |
| 考试次数未超限，且没有不允许的并发考试 | 创建考试记录 |
| 交卷、判分、取消等状态转换合法 | 更新考试记录 |
| 考试总分与逐题实际得分一致 | 判分完成 |

对于创建考试记录、扣减考试次数、提交答案和交卷等操作，应结合事务与并发控制，避免重复提交或并发请求破坏数据一致性。

## 6. 索引与唯一约束的业务含义

索引不仅用于加速查询，也承载部分业务约束。

| 约束或索引 | 作用 |
|---|---|
| `uk_user_name` | 用户名唯一 |
| `uk_role_code` | 角色编码唯一 |
| `PRIMARY KEY (user_id, role_id)` | 用户角色关联不可重复 |
| `uk_key (question_id, option_key)` | 同一道题的选项标识不可重复 |
| `uk_sort (paper_id, sort)` | 同一试卷的题序不可重复 |
| `uk_question (paper_id, question_id)` | 同一题目不能重复加入同一试卷 |
| `uk_user_exam_no` | 同一用户的考试序号不可重复 |
| `uk_attempt_question` | 同一考试记录中的同一道试卷题目只能有一条答案记录 |

普通索引则主要服务于常见查询路径，例如题库列表筛选、考试活动状态筛选、用户考试记录查询和进行中考试的截止时间扫描。

索引是否真正有效，仍需结合实际 SQL 的 `WHERE`、`JOIN`、排序方式和数据规模，通过 `EXPLAIN` 验证。

## 7. 当前模型的重要边界与注意事项

### 7.1 题目快照是历史稳定性的关键

`paper_question.question_snapshot` 应作为已发布试卷的题目内容依据。发布后，不应通过修改源题目来改变既有考试的题干、选项和标准答案。

实际实施时，快照应有明确的数据结构约定。若将选项顺序、选项标识和标准答案存入快照，判分也应基于同一份快照，避免快照内容与实时源数据混用。

### 7.2 发布后的试卷应采用版本化思路

当前模型没有独立的试卷版本表，也没有为 `exam` 增加试卷版本号。因此，最简单可靠的业务规则是：

- 草稿试卷允许编辑。
- 已发布且已被考试活动使用的试卷，不直接修改题目集合、题序和分值。
- 需要调整内容时，复制或创建新试卷，再发布新的考试活动。
- 历史考试始终保留原有的试卷题目快照和评分依据。

这属于应用层生命周期约束，不是数据库当前自动提供的能力。

### 7.3 考试记录引用试卷题目时必须校验归属

`exam_answer.paper_question_id` 与 `exam_attempt.exam_id` 之间没有直接的数据库约束。服务端必须通过以下关系校验：

`exam_attempt → exam → paper → paper_question`

确保答案引用的试卷题目确实属于本次考试活动使用的试卷。仅检查两个 ID 都存在是不够的。

### 7.4 自动判分和人工判分的完成状态需要统一

`exam_attempt.status` 中的 `submitted` 和 `graded` 应有明确语义。例如，全部客观题判分完成但简答题尚未人工评分时，考试应处于什么状态？总分是否允许暂时为空？结果页何时展示最终成绩？

当前结构允许通过 `user_score`、`is_passed` 和 `graded_at` 的空值表达尚未完成评分，但服务端必须统一判分流程，避免出现“已判分但仍有题目未评分”等不一致状态。

### 7.5 当前模型不保存作答历史版本

`exam_answer` 采用每题一条记录、反复更新的设计，适合 MVP。它记录当前有效答案，但不保留每一次修改的历史。如果未来需要审计考生的修改轨迹、自动保存版本或争议复核，再增加作答事件表即可。

### 7.6 当前权限模型不是完整的 RBAC 权限系统

`user`、`role`、`user_role` 只实现用户和角色的关联。若系统后续需要菜单、按钮、接口或数据范围权限，还需要进一步建模权限实体及其与角色的关联。

## 8. 设计结论

当前 11 张表形成了一条职责明确的业务链路：

- **题库层**维护可复用的题目内容。
- **试卷层**固定题目组合、顺序、分值和发布快照。
- **考试层**定义开放规则和参加限制。
- **作答层**记录每次考试的答案、评分与最终成绩。
- **身份层**维护用户及角色分配。

整个设计的关键不在于表的数量，而在于隔离源数据、考试规则与历史记录。尤其是 `paper_question.question_snapshot`、`exam_attempt` 中的规则快照字段，以及 `exam_answer` 的逐题记录，共同构成了历史考试可追溯、成绩可复核的基础。

当前模型适合先实现题库管理、手动组卷、考试发布、在线作答、自动判分与成绩查询。复杂权限、完整试卷版本体系、作答审计和更复杂的评分规则，可以在实际业务需求明确后再扩展，而不必提前引入额外的表结构。
